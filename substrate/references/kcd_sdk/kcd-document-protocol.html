KCD Document Protocol — Canonical Reference

Why

authoring, parsing, validating, or rendering any KCD document

This is stone. The locked specification for how a KCD artifact is encoded as an HTML document. Drift here is costly — it ripples through the parser, the validator, the renderer, the editor, and every authored and crystallized artifact. Change this only with an explicit ruling, never incidentally. Reference implementation: _Claude/work/lens-crafter/html-proposal/lens.html + _Claude/kcd.css. Origin trial: _Claude/work/lens-crafter/html-proposal/. Migration plan: html-substrate.

Substrate: standards-valid HTML — opens and navigates in any browser, rendered dark via one shared kcd.css, read mechanically by Starmind. No proprietary format. A small, closed set of data-kcd-* attributes carries all machine meaning.

1 · The addressing contract (the core law)

  1. Every machine value is an addressable field: data-kcd-field="<name>". The field's own content is the value — the element's text, or its href when the field is a link.
  2. One element, two duties. The same element surfaces the text to the human and is the machine address. No separate machine copy, no duplicated data-x="…" + visible span.
  3. No brittle dependencies. The parser reads only explicit data-kcd-* attributes and data-kcd-field values. Never element order, never grid position, never class names, never scraped free text. Anything not addressed is human chrome the parser ignores.
  4. Greppable, then fast. grep 'data-kcd-field="where"' finds every reference target in the corpus today; the explicit format lets faster structured tools be built tomorrow.
  5. File-level, all-or-nothing validation. Every field declares a data-kcd-type; each type maps to a tiny validator function. If any required field is missing or fails its validator, the whole file is discarded and ignored — never partially parsed. A document is not active until it validates. This is what keeps malformed data out of the system.
  6. Validators are shared. The per-type validator functions are a small composable library reused by SettingField — the same data-kcd-type vocabulary drives both document validation and the inline editor's controls.
  7. Reference implementation. The binary validator is kcd_sdk's KcdValidate (kcd_sdk/src/core/html/KcdValidate.ts), built on the Node-free HtmlTree reader and the KcdAddress grammar — pure JS/TS, no DOM dependency, file-level all-or-nothing exactly as above.

1.1 · Links and addresses (2026-07-22)

A link asserts occupancy. An address does not.

<a href="…"> means there is a document there, go read it. The validator probes every one, and a miss is a warning — correctly, because the sentence containing it is false when the target is absent.

<code data-kcd-address> means this is the location. Something may occupy it now, may occupy it later, or may never arrive. Vacancy is a legitimate state and is never reported as an issue. This is the encoding for:

  • output declarations — a path an artifact writes to when it runs; absent until then, and absent in every freshly installed vault
  • forward references — a document that is planned but not yet authored
  • ephemeral space — work/, logs/, scratch/, reports/, audits/, dev-utilities/, which are indexed: false by registry and are not installed into a user’s vault at all
  • non-artifacts — source files, directories

Form. The visible text is the address; the attribute is a bare marker, so §1’s one-element-two-duties rule holds with no machine copy:

<code data-kcd-address>_Claude/reports/audit-consistency.html</code>

When the prose must read differently, the attribute carries the value, exactly as href does:

<code data-kcd-address="_Claude/reports/audit-consistency.html">the consistency report</code>

As a typed field — frontmatter, or a faux-table cell — the type is data-kcd-type="address", and the value comes from text content like every other non-link type. todo and completed are addresses for exactly this reason: a lens declares where its log lives, it does not assert that one has been written.

Two value shapes. An artifact name (a slug) resolves through the same name index base and lens already use, and therefore survives any move, with no machinery involved. A path is project-root-relative, for targets that have no name.

A path-form address is repointed on a move — amended 2026-08-18; this paragraph previously said the name was the only form that does not rot when a file is relocated, which was true when written and is not now. kcd_move's text pass rewrites data-kcd-address alongside href, so the location an address names stays true. That is a repair, not a guarantee: it reaches only where the sweep reaches, and it repoints the location claim without ever asserting occupancy, which stays outside the protocol. Prefer the name whenever the target is, or will be, a KCD artifact — the preference stands, for the better reason that a name needs no repair at all.

Validation. An address is checked for well-formedness only — a valid slug, or a valid project-root-relative path with no ../ chain and no absolute root. A malformed address is an error. A well-formed address pointing at nothing is silent. Vacancy may be inventoried on request (Vault.vacantAddresses), never in the health stream — otherwise the primitive merely relocates the noise it exists to remove.

The one prohibition. An artifact must never <a href> into indexed: false space. Occupancy there can never be asserted, so the link is false by construction — whether or not the target happens to exist on the authoring machine. The banned set is derived from VaultLayout, never hand-maintained.

Never a slot, never routed, never compiled into context

A field value's source by type: link fields (where, paths, urls) → href; all others → text content.

Structural rule — no empty containers. Include a region (or section) only when it carries content. Never emit an empty Know / Care / Do. An artifact uses only the structure it needs — most non-lens artifacts use few regions or none. (How much a single artifact should carry is left to judgment: a habit must stay atomic, not larded with fifty things. No mechanical cap yet.)

Structural rule — a DECLARED section keeps its declared name, and the heading must match. data-kcd-section is not free text where a shape has spoken. Every artifact type declares its shape — which section names it carries, and in what order — and a document of that type may not rename or re-spell one of them. A habit's declared set is why · action · explanation · rules · references; spelling why as when because it reads better is a validation failure, not a passthrough — the file is refused whole, per the all-or-nothing rule in §0. The visible heading is bound to the same set: a why section is headed Why. This is load-bearing for anything that reaches the Manifest, because merge and compile both key on the section name — two documents of the same type are only mergeable if why means why in both.

Whether an UNDECLARED section is legal is per type, and only lens is closed. KcdShapes marks every type open: true except lens, and that asymmetry is closed by evidence rather than by preference: an undeclared lens section is silently dropped by the compiler, so it fails exactly where an author cannot see it. No other type pays that cost, so no other type is refused for carrying a section its shape has not named. A type that genuinely needs a new section as part of its contract still gets it added to the shape, where every document of that type inherits it — never invented at one call site.

Structural rule — HTML comments are a HUMAN channel, and a write strips them. Ruled 2026-08-17, mechanism settled 2026-08-24 (Bryan). An agent must never read a comment and never author one: it has the document body for anything it needs to say, and a side channel an agent can write but a reader does not expect is a contamination surface — the opposite of what these documents are for. A comment is documentation for whoever opens the file, and a person is free to hand-author HTML carrying as many as they like. The mechanism is STRIP, not preserve. HtmlTree.parse skips <!--…--> without creating a node and KcdSynth.proseToHtml strips the syntax out of prose, so both input paths already yield nothing and no HtmlComment node enters the union. Preserving them badly would be worse than dropping them: HtmlTree.textOf recurses into anything that is not an element, so a naively preserved comment would return its own prose straight into compiled context — handing agents the exact thing the ruling forbids. The cost accepted here is that a comment a human wrote does not survive a write through the tools; author it in a file the tools do not rewrite, or put it in the body where it belongs.

Where doctrine belongs. An open type accepting an extra section is not an invitation to grow one. A habit that has accumulated authoring or format doctrine should point at a reference rather than carry it — see habit-authoring, which is where that material now lives. A habit stays atomic; a reference is what holds a spec.

3 · Faux-tables (never a real <table>)

What/Where/Why-shaped idioms (References, Domains, Habits, Contracts, Parameters) render as styled divs, not <table>:

<div data-kcd-table>
  <div data-kcd-head><span>What</span><span>Where</span><span>Why</span></div>
  <div data-kcd-slot="reference" data-kcd-mode="on">
    <span data-kcd-field="what"  data-kcd-type="text">Framework concepts</span>
    <a    data-kcd-field="where" data-kcd-type="path" href="…/kcd_framework.html">kcd_framework</a>
    <span data-kcd-field="why"   data-kcd-type="text">the primitives this lens enforces</span>
  </div>
</div>
  • data-kcd-head is human chrome (column labels); the parser ignores it.
  • Each row is a component (data-kcd-slot / data-kcd-param); each cell is an addressable field.
  • Columns via the --kcd-cols custom property. Canonical column order: What / Where / Why.
  • Order is cosmetic — fields are read by name, so a reordered or renamed cell breaks neither parse nor render.
  • data-kcd-slot is canonical-only. A slot row's cells must be data-kcd-fields. Never put data-kcd-slot on a row you are not addressing — an unaddressed slot is invalid (the file fails).
  • data-kcd-slot carries its kind, by position. Every slot is data-kcd-slot="<kind>" from the closed set (§2); the parser reads it directly and never infers type from the where href. Kind follows the BLOCK: a References / Domains block yields references, Habits habits, Contracts contracts, Tools tools, Rules rules; any other block yields link (a row carrying a link) or table-data (a row with no link). Only the five dredge roles are routed / dredged — link and table-data ride their region as plain content, never as affordances.
  • Illustrative tables are chrome, not faux-tables. A descriptive table in prose (common in framework / reference docs) carries no canonical data — author it as a plain <table>. The parser ignores any <table>, and a <table> may never carry data-kcd-field / -slot / -param. Bright line: data-kcd-slot ⇒ canonical; <table> ⇒ chrome.

5 · Audience & chrome (dual extraction)

The same surface yields two automatic extractions, chosen by consumer context:

  • Human read — the full visual: frontmatter panel, demos, styling. Optimized for the eye.
  • AI read — chrome stripped, optimized for brevity.

data-kcd-audience="human|agent|both" (default both) on any element is the strip control; human nodes are kept for the visual read and dropped from the AI read.

Chrome components (all human-audience by nature):

  • Living demo — data-kcd-chrome="demo": an interactive area (rendered in Starmind, placeholder in a plain browser).
  • Live widget — data-kcd-live="<id>": an embedded Starmind widget; inert placeholder elsewhere.
  • Bespoke vanilla JS — <script type="text/kcd-js" data-entry="<fn>">…</script>: the canonical insertion point for custom JS. The non-standard type means it does not execute in a browser (the script-exec gate stays closed outside Starmind, which extracts and sandboxes it). Source is shown to humans, stripped for the AI.

6 · Composable rules — habit-class and the cascade

A habit-class is a named mutual-exclusion group ("textual radio-buttons"): a set of behaviors where, by definition, only one may apply (e.g. spawn-subagent = { spawn-subagent-never, always-use-subagents }). Classless habits are additive (all apply, union); classed habits are subject to the cascade below. Declared on a habit's own frontmatter (habit-class); mirrored on the including slot (data-kcd-habit-class), validated to agree.

Carriers (the first composition rule). Habits may be applied to exactly three things — a Lens, an Agent, or injected in a Workflow. No other artifact type carries habits.

Cascade priority — highest wins: Workflow > Agent > Lens. A lens-level habit is the base default; an Agent or a Workflow can override it. This is a one-dimensional override — like a primitive CSS cascade whose only specificity axis is the carrier level.

Resolution:

  • Within one carrier, including two habits of the same habit-class is a parser error — the file is discarded.
  • Across carriers, for each habit-class the highest-priority carrier that specifies a member wins; lower-level members of that class are overridden (dropped).
  • Classless habits never conflict — they union.

This is the spine of the composable-rules feature. Open: how an override surfaces in the UI (which habit won, which were overridden).

7 · Skill alignment (we are a superset)

KCD maps onto the Anthropic Agent Skills standard rather than redefining shared terms:

  • name + description adopt the SKILL.md field names and constraints (§4).
  • Dredge = progressive disclosure. data-kcd-mode="suggested" ⇒ full text always-loaded (Skill Level 1–2); on (the default, no attribute needed) ⇒ available-on-request, a routing row only (Level 3 / bundled resource); off ⇒ excluded entirely, not even a routing row.
  • No invocation command — KCD artifacts, like Skills, are description-triggered. This retires the whole command family: the lens !{name} command, the generator/analyzer #{name} task tag, and the session-log !{lens} token. CLAUDE.md may keep !lens / log shorthands as a Claude-level hook, but they are not KCD canonical and appear in no authored artifact.
  • Folder + bundled resources ↔ a lens folder + context/ + its slots.

8 · Rendering & theme

  • Dark by default. Light is a future productization theme — it overrides only the :root variable block in kcd.css; every component reads the variables.
  • One shared kcd.css styles every component by keying off the same data-kcd-* addresses the parser reads — styling and parsing share one contract.
  • Links navigate natively in any browser; chrome is inert outside Starmind.

8.1 · The stylesheet (amended 2026-08-17 — two tiers)

Canonical file: kcd.css, at the vault root. One copy, no duplicates. A vault created before 2026-07-26 keeps it at kcd/kcd.css and is not wrong — the href is computed from where the file actually sits, never from an assumption that it sits at the root.

Every document carries TWO tiers, in this order:

<style> …the baseline, under ten lines… </style>
<link rel="stylesheet" href="../../kcd.css">

Tier 1 — the inline baseline. Legibility, never design. Background, text colour, link colour, a readable measure, and enough on code that inline spans do not vanish. That is the whole remit. If it exceeds ten lines it has stopped being a baseline and started being a second design language, which is the failure this tier exists to avoid. It is not a copy of kcd.css and must never grow toward one: a full inline copy would be ~10 KB per document, would go stale the moment the stylesheet changed, and would put a corpus one commit away from an every-file diff. A baseline that sets two colours never goes stale, because an out-of-date copy of "dark background, light text" is still correct.

Tier 2 — the linked stylesheet, RELATIVE. One ../ per directory level from the document to wherever kcd.css sits in that vault. This is the real design language, and it overrides the baseline wherever a stylesheet can actually load.

Cascade order is load-bearing and is not a style preference. The <style> block comes FIRST and the <link> SECOND. Both set body at identical specificity, so the later declaration wins and the real stylesheet overrides the baseline. Reversed, the nine-line baseline silently beats kcd.css in every browser — a page that looks fine, styled by the wrong sheet, with nothing anywhere to indicate it.

Why this replaced the absolute href. The 2026-07-29 rule made every document carry one configured absolute file:/// URL, reasoning that a computed relative href duplicated depth math between the emitter and a corpus-wide repair verb. That was sound about duplication and wrong about the problem. An agent-facing viewer commonly cannot load an external stylesheet at all — relative or absolute makes no difference, because the document is rendered detached from its directory and a reference of ANY kind has nothing to resolve against. It fails silently: no warning, just an unstyled page. So the choice was never absolute-versus-relative; it was reference-versus-carry, and the answer is carry the minimum, reference the rest. Absolute additionally loses on its own terms: it names one machine's filesystem, so a vault under version control styles nothing after a clone.

The duplication objection is answered, not ignored. The depth math lives in exactly ONE function — KcdEmit.cssHrefFor — which the emitter and the corpus sweep both call. There is no second copy to drift, which is what the 2026-07-29 ruling actually wanted; it achieved it by deleting relativity rather than by consolidating the math.

Where the value lives. Daedalus daedalus/src/Config.ts resolves it through the same four tiers it resolves the vault root through — most specific wins:

TierSourceSet it by
1argument--css <path> on the CLI or the server entry
2host slicea host's own config screen — in Starmind, the KCD Library package's Stylesheet path field
3environmentDAEDALUS_CSS_PATH
4derivednothing — falls back to this vault's own kcd.css, which is why a fresh install already works

What the configured path is FOR, now that the href is derived. The tiers above still resolve one value — where kcd.css actually lives on this install. It is no longer embedded in a document; it is the input the depth math measures FROM. The emitter takes the stylesheet's location relative to the vault root ( kcd.css in a current vault, kcd/kcd.css in a pre-2026-07-26 one ) and prefixes one ../ per level of the destination's own depth. A Windows path pasted from Explorer still configures correctly, and one config drives vaults with different layouts without either being special-cased.

What an agent should do: never construct a stylesheet link. Write through kcd_save and both tiers are correct — the emitter builds the head from scratch on every write, so a document self-corrects the moment anything saves it. If you are hand-authoring outside the tooling, copy BOTH the <style> block and the <link> from a neighbouring document at the same depth, and keep them in that order. A document at a different depth is the one case where copying is wrong.

The head is generated chrome, not data — which is why the emitter owns this. KcdParse takes only HtmlTree.innerHtml( article ) as the artifact's body, so the head never enters the object model: no kcd_get, no kcd_compile, and no agent read ever sees the baseline or the link. KcdValidate likewise validates from <article> down and never inspects the head. The head is therefore discarded on read and rebuilt on every write, which is what makes two tiers affordable — the baseline costs disk, never context, and it cannot drift in a document that anyone edits.

Unrelated to §1.1 addressing. The rule that body paths are vault-root-relative <a href="_Claude/…"> links is a different rule with a different reason, and it is unchanged. The stylesheet is still not an address: nothing links to it, no heal rewrites it, and no validator reads it. It is a browser asset — which is now exactly why it needs a relative href a browser can follow AND a baseline for the readers that will not follow one.

Two known gaps, both deliberate. KCDPrimitive.toHtml() calls emit() with no href and therefore produces the bare-filename fallback (it is a serialization helper, not a write path — do not use its output as a file). And daedalus fix-css walks only documents that parse, so a malformed file is passed over without a report — its totals are "of the documents that parse", never "of every document". It is load-bearing again: an existing corpus carries no baseline until it is swept, and until then those documents are unreadable in any viewer that will not load a stylesheet.

9 · Scope — what stays outside the substrate

The rule: every KCD primitive — lens, contract, habit, generator, analyzer, template, reference, plan, nav-index — and every document that describes or points at one, is authored as .html per this protocol. No exceptions, and no new primitive type is ever authored as .md. work/ is the sole grandfather clause: pre-2026-07-01 drafts left there are not back-converted, but anything new written to work/ is HTML from the start (see the plan contract's "every plan is HTML, at every stage" rule for the concrete case).

What is exempt — not KCD documents, so this protocol does not govern them:

  • Session, todo, and completed logs — _Claude/logs/session.md, _Claude/logs/{lens}/todo/todo.md, _Claude/logs/{lens}/completed/completed.md. Append-only breadcrumb lines, not dual-audience artifacts — see the log-session-liberal habit (one of two poles of the log-session mutual-exclusion slot — see §6).
  • Chat transcripts — _Claude/logs/chats/*.md. Raw session capture, not an authored document.
  • Raw generator/analyzer output — _Claude/audits/**, _Claude/reports/**, and a generator's own deployed context/ config/data files (e.g. an output-contract.md, a run-log.md). These are machine-written run records and config, the same kind as a registry — not something a human or agent reads as a document in its own right.
  • External standards — CLAUDE.md, SKILL.md, AGENTS.md. Conventions owned outside KCD (Claude Code, the Agent Skills standard); this protocol has no authority to reformat them.
  • Docs a generator writes into a target codebase it is not itself part of — e.g. safe_work/docs/front-end-component-map.md. That codebase's own documentation conventions govern, not this one.

Anything not on this list that is still .md outside work/ is drift, not a legitimate exception — flag it.

10 · Seeds — payload carried, not compiled

§9 puts a small set of files outside this protocol, CLAUDE.md and its siblings most of all. A seed is how a governed HTML artifact authors one of them: a literal payload block carried inside the document, extracted at deploy and written to a file this protocol does not govern. The artifact is the source and is never copied; the emitted file is a product. This is the sanctioned bridge across the §9 boundary — it lets an external-standard file be authored, versioned, and reviewed as a KCD document without claiming authority over its format.

Container. A seed is the §5 non-executing script idiom with a markdown type:

<script type="text/kcd-md"
        data-kcd-seed="claude"
        data-kcd-target="CLAUDE.md"
        data-kcd-mode="prepend">
# Heading

Markdown, verbatim.
</script>

Why a <script>, and why it is inert. On first encounter, script blocks sitting in a governed artifact read as an injection surface. They are not, and the reason belongs here rather than in a doc-comment someone has to go find. A seed needs a container that holds an arbitrary text payload byte for byte — markdown carrying its own <, & and >, which any ordinary element would turn into entities. HTML has exactly two raw-text elements, <script> and <style>, and only one of them accepts an arbitrary type. It is the only standard container that keeps the payload unaltered.

Inertness comes from the type attribute, not from anything KCD does. A script with an unrecognized type is a data block by the HTML standard: not executed, not rendered, not parsed as script. That holds in every reader, including one that has never heard of KCD — which is the point, because it is a guarantee this project does not have to be trusted for. Two further layers sit on top. A host that injects KCD bodies into a live DOM rewrites the block to an inert <pre> source view first, so a human still reads the payload and nothing runs — that is an additional defence available only to hosts that render, never the thing the guarantee rests on. And the context compiler strips seeds outright, so a payload never reaches a model as context at all.

No escaping, in either direction. Script content is raw text, so a payload is authored with its literal characters and carries no entities. The writer honours the same rule: raw content round-trips verbatim through parse and serialize, so a save cannot add a layer the author never wrote. That symmetry is pinned by test, because it was broken once — serialize escaped raw content until 2026-08-13, and a payload containing a markdown blockquote would have reached a real project's CLAUDE.md with &gt; in it.

The one sequence a payload may not contain is </script. There is no escaping around it: entity references are not decoded inside raw text, so &lt;/script would place those literal characters in the emitted file rather than protect anything — the file would look repaired and be corrupt. The sequence must simply not appear; split it at the source (<\/script in JavaScript) or reword. A writer handed one refuses the whole document rather than emit a file that reparses into a different tree, which is the shape every raw-text breakout takes.

  • data-kcd-seed="<host>" — required, a slug naming the agent host this payload is for (claude, codex, gemini). One document carries one block per host; the extractor selects by this key. Host keys are open, not a closed set — a new host is a new block, not a schema change.
  • data-kcd-target="<filename>" — required, the file written, resolved from the project root rather than the vault. A seed missing its target fails the file, per §1.5.
  • data-kcd-mode — prepend (default) or create-only.

Modes. create-only writes the whole file and never touches one that already exists. prepend maintains a managed block at the top of the target, delimited by <!-- kcd:begin --> and <!-- kcd:end -->; re-extraction replaces only what lies between the markers and leaves everything below them alone. That is what lets a vault deploy over a project whose CLAUDE.md already says things of its own, and re-deploy later without clobbering them.

Seed targets double as the install's file registry. Nothing hand-keeps a list of what an install put into a project: installedPaths() reads the seed declarations and returns their targets alongside the Model Context Protocol registration file. That is what lets an uninstall remove exactly what the install added, and it is the second reason adding a host is a new block rather than an edit in two places — the block IS the registration.

A seed is not a slot. It carries no data-kcd-field cells, is never routed or dredged, and belongs to no faux-table. The two are unrelated primitives that happen to share an English word: data-kcd-slot is a routing row (§3), data-kcd-seed is a payload block.

Seeds never compile. The context compiler strips every seed block, exactly as it strips chrome (§5). A seed is deploy input, not agent context. A document carrying three host payloads would otherwise triple itself on the wire — and each payload is prose written for an agent that has not read the vault yet, which is precisely the wrong thing to hand one that has.

Resolved & still-open

Resolved (now stone): names are kebab-case (Skill standard; the leading _ on framework scaffolds is a sort prefix, not part of the name); regions are optional (§2 no-empty rule); the frontmatter field set (§4) is locked; the habit composition cascade (§6) is locked; author is universal, block form; domain (a special tag, may overlap) retires category; the template target field is dropped (inferred from filename); utility is not a document type (it is declarative code — UtilityObject); tables (§3) — data-kcd-slot canonical-only, illustrative tables are plain <table> chrome; a slot carries its kind explicitly and by block-position (dredge roles reference/habit/contract/tool/rule, domains folding into reference; non-dredge link/table-data), retiring href-inferred typing; templates are exempt from validation; the reference validator is pure-JS + binary; model is a parameter (§4); composed is a legal status; the command family is retired (§7); the index scaffold is _nav-index_template.html. The artifact-type set now includes note (a forward-looking observation — keeps its open / candidate sections, unlike a reference) and how-to (a procedural recipe — keeps its own step shape); observation is a legal (note) status; the non-HTML scope (§9) is locked — logs/chat-transcripts/raw-generator-output/external-standards/target-codebase-docs are the only legitimate .md, everything else is drift. The seed component (§10) is the sanctioned bridge to those exempt files — payload carried in HTML, extracted at deploy, stripped from compiled context; it is a distinct primitive from data-kcd-slot and shares nothing with it but the English word.

Retired — must NOT appear in any authored document: command / invocation (incl. the #{name} task tag and !{lens} log token — only CLAUDE.md keeps the !lens shorthand) · pipeline (superseded by Workflows) · index as a type name (→ nav-index) · category (→ domain) · the template target field · utility documents.

Still open (judgment for now): how much a single artifact may carry (atomicity vs. larding — no mechanical cap); UI surfacing of habit overrides (which won, which were dropped).
