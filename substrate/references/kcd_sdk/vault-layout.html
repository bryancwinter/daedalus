Vault Layout — SDK Reference

Why

navigating a KCD vault, deciding where a new artifact belongs, or changing anything that classifies, indexes, or deploys the directory structure

A KCD vault is one directory — the doc root, conventionally _Claude/ — sitting inside a project root. The folders beneath it are not a convention to be remembered; they are a table in code. VaultLayout (VaultLayout.ts) is that table, and it is the machine-readable authority. Three consumers read it and nothing else defines the structure:

  • Classification — a path to its artifact type (VaultLayout.classify, which the SDK's classifyRelPath and LensObject.classifyByPath both resolve through).
  • The library index whitelist — which top-level folders the artifact index descends into (VaultLayout.indexedDirs).
  • The deploy scaffold — the empty directories a new project gets created with. What FILLS them is InstallManifest's job, not this table's.

Before the table these three were written down separately and had already drifted; the whitelist carried a plans_complete/ folder that has never existed at the top level. One table is the fix.

Authority

The code is authoritative; this document is its published face. The table below is maintained alongside VaultLayout.ts — when they disagree, the code wins and this document is the thing that is wrong. Change a row there first, then reflect it here. An agent that needs the exact machine-readable rows should read the source; this document exists so the reasoning — what each folder is for, and why some are excluded — is legible without reading TypeScript.

The two layers

Every directory belongs to exactly one layer. The layer answers "who owns this and how does it get here?"

  • agent — the Know + Care + Do artifacts an agent is composed from. Authored per project.
  • data — everything a project accumulates as it runs: knowledge it has distilled, agreements it has made, and the output and scratch its work produces.

The structure

Paths are relative to the doc root. Indexed means the artifact library walks it; an unindexed folder still exists and is still used, it simply holds nothing the library should catalogue.

Substrate — retired from this table ( 2026-07-25 )

A vault used to carry its own canonical mirror under a kcd/ row here, with a kcd/templates/ row beneath it. Both are gone: canonical is not deployed — the framework's master copy lives in the installed Daedalus package, and a deployed vault holds no kcd/ folder at all. What fills a vault is now a separate table, InstallManifest, which maps bundle source → vault home → required | optional. This table describes empty structure only; that one describes what lands in it.

Agent layer

WhatWhereWhy
lenses/ — lens · indexed lenses/ Know+Care personalities. One folder per lens, each holding its lens file and a context/ of support material.
analyzers/ — analyzer · indexed analyzers/ Read-anywhere, write-one-report agents.
generators/ — generator · indexed generators/ Manifest-driven write agents — broad write authority, no judgment of their own.
habits/ — habit · indexed habits/ Atomic behavior fragments. Flat files, no subfolders.

Data / output layer

WhatWhereWhy
references/ — reference · indexed references/ The project knowledge store, categorized by folder — the folder IS the category. A reference exists only here.
contracts/ — contract · indexed contracts/ Behavioral agreements — composable prose a third party can evaluate against.
utilities/ — utility · indexed utilities/ The registered tool tier — draft/ (unapproved) and deployed/ (approved), with a registry.
plans/ — plan · indexed plans/ Promoted plans that authorize action, plus the plans_complete/ and plans_deferred/ buckets beneath. Those two are nested, not top-level — they classify as plan through their parent.
work/ — untyped · not indexed _Claude/work/ Per-lens scratch space (AI/, human/, plans/). Cheap and discardable until something is promoted out of it. A plan here does not authorize action.
logs/ — untyped · not indexed _Claude/logs/ Session log plus per-lens completed/, todo/, and agent-status/.
reports/ — untyped · not indexed _Claude/reports/ Analyzer output.
audits/ — untyped · not indexed _Claude/audits/ Generator raw output and vault backups. Deliberately unindexed — backup copies of the vault living here are what once made the library accrue duplicate references.
scratch/ — untyped · not indexed _Claude/scratch/ Free scratch space with no per-lens structure.
dev-utilities/ — untyped · not indexed _Claude/dev-utilities/ The dev command deck — a JSON-declared list of scripts run against the project. Tooling, not governed artifacts.

Classification rules

A path resolves to its type by the table, with three rules that run first because none of them is decided by which folder a file sits in:

  1. A nav-index is a nav-index anywhere. Any file named nav-index.html classifies nav-index regardless of its folder — it is a navigational primitive, not a member of its parent's category.
  2. Anything under a context/ folder is a reference. context/ holds support material for whatever owns it — a lens, an analyzer, a generator — and support material is reference material.
  3. Inside lenses/, only the lens's own file is the lens. lenses/{name}/{name}.html is a lens; anything nested deeper is reference.

Then the table, matched by longest directory prefix, so a more specific row always beats a shorter one it also sits under. Longest-prefix rather than table order means adding a row can never silently change how an existing one classifies.

What is not in the table

A directory absent from the table classifies unknown and is never indexed. Absence is the safe default, and it is what gives the index whitelist teeth: a fresh audit dump or a stray folder cannot leak artifacts into the library until someone deliberately adds a row.

This is why the untyped folders above are listed rather than omitted. They are real, expected parts of the structure — a deploy needs to create them, and agentic work generates drift and throwaway content quickly, so it matters that there are sanctioned places for it to land. Listing them with no type distinguishes "known, holds nothing to catalogue" from "unrecognized", which are genuinely different signals.

Deployment

Every row in this table is created as an empty directory, which is what lets a vault be installed into any directory — fresh, or wrapping code that already exists. Rows used to carry a scaffold mode distinguishing "create empty" from "fill from the canonical master"; that field was retired on 2026-07-25 along with the substrate rows, since every remaining row is created empty and filling is InstallManifest's job.

A deploy is idempotent — anything already present is left alone — so the same operation both creates a new vault and repairs an incomplete one.
