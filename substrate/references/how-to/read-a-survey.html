Read a Survey

Why

you need to orient in a codebase you have not seen, and a survey exists for it under audits/survey/

A survey is what a project looks like from the outside, computed rather than described. It is produced by walking the tree and reading filenames — no source is parsed, no model is involved — so it is the same answer every time, and it works on a Python, Go or C# project exactly as well as a TypeScript one.

Read the survey instead of exploring. That is the whole point of it. Exploring a strange repository costs many turns and produces claims you cannot support; the survey costs two file reads, and every fact in it came off the disk.

1 · The shape — a flat tree, two hops deep

The survey is a directory of JSON files, not one document. It is deliberately flat: one roster plus one file per component, all siblings.

audits/survey/
  index.json          the roster — every component, one line each
  root.json           one component
  starmind.json       one component
  kcd_sdk.json        one component
  ...

Every file names its own schema (survey/1). Extra keys may appear in later versions; ignore what you do not recognise rather than failing.

2 · How to read it

  1. Open index.json. It lists every component with an id, a kind, its path, a one-line description, and the file that describes it in full.
  2. Decide which component matters for the task in front of you. Usually that is one or two of them, not all.
  3. Open that component's file. Everything known about it is in there — languages, entry points, test layout, what it contains.

Do not read every component file. The roster exists so you do not have to.

3 · What a component is

A component is the unit of a survey: the project root, plus every directory carrying its own package manifest (package.json, pyproject.toml, go.mod, Cargo.toml, a .csproj, and so on). In a monorepo each package is its own component. In a single-package repository there is one, plus the root.

Every file on disk is attributed to the deepest component containing it, so counts never double up and a monorepo reads as its real parts rather than one averaged blur.

FieldWhat it means
idShort, stable, filename-safe. Two components with the same directory name widen leftwards through the path (daedalus and mcp-daedalus), so an id always says which one.
kindapplication · library · plugin · tool · docs · unknown. A coarse reading of the manifest and the location. unknown is a legitimate answer.
pathRoot-relative, forward slashes. . is the project root itself.
descriptionA generated sentence. A prototype, not a claim — see below.
languagesExtension census, ranked by file count. Names what is present; says nothing about what matters.
entryPointsWhere execution starts. source: "manifest" means a manifest declared it — that is evidence. source: "convention" means the path merely exists and matches a common pattern — that is a guess.
testsDirectories and the filename conventions actually observed. A shape, not a coverage figure.
containsIds of components nested beneath this one, by nearest enclosing component.
statsFile and byte counts. Useful for ranking; skip it when reasoning about meaning.

4 · What a survey does NOT tell you

This section is the load-bearing one. A survey is a census, and a census is confidently silent about most things. Treating it as more than it is produces exactly the confident-wrong answer it exists to prevent.

  • It does not know what the code does. No source was parsed. A component full of TypeScript might be a compiler or a to-do list; the survey cannot tell you which, and neither can you from reading it.
  • It does not rank importance. File counts are size, not significance. The most important component is frequently one of the smallest.
  • A convention entry point is a guess. The file exists and has a conventional name. Nothing confirmed it runs.
  • The description is machine-generated. It is a starting sentence, meant to be replaced by someone who knows the project. Quote it as a summary of the survey, never as a statement about the project.
  • Absence is not evidence of absence. Build output, dependency and vendor directories are never walked, and the walk stops at a file cap. When limits.truncated is true the survey is a partial view, and you must say so rather than conclude a thing does not exist.
  • It is a snapshot. The directory is flushed and refilled on every run; generated is when. A survey older than the working tree describes the past.

The honest posture: synthesise what you were handed, never make claims about a codebase you inferred. Where the survey is silent, say so and go look.

5 · Status — experimental

The survey is a prototype for document architecture and a temporary artifact. The open question it exists to answer is whether a non-frontier agent can genuinely orient from it, read cold, without any of the reasoning that produced it. If it can, the survey is a candidate substitute for hand-written orientation prose and a research path in its own right. If it cannot, the shape is wrong and should change.

Treat the structure as unsettled. Do not build anything that depends on a field staying where it is.
