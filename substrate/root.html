Entry Document

Why

Starting any session in this project, on any agent host — this is the first thing to read, and the thing every entry file points at.

Where you are

This project uses KCD — a meta-cognition layer that splits an agent's context into three parts assembled at runtime: Know (what you need to know), Care (what you defend), and Do (what you are doing this session). A lens is a Know + Care pair — a personality with no actions. A session is a lens, or a stack of them, plus a Do.

The point of all this: an agent that loads a lens does not have to rediscover the project. The things a newcomer would take a week to learn — why a thing is done the odd way, what must never be changed, which decisions are already settled — are written down once and loaded on demand.

The vault is _Claude/. Everything governed lives there, authored as standards-valid HTML that opens in any browser and is read mechanically by the tools. The CLAUDE.md / AGENTS.md / GEMINI.md file at the project root is a pointer to this document. Its managed block is generated from root-context, so edit that rather than the emitted file; anything below the block belongs to the project.

_lens-base is the auto-loaded floor. It carries the project-wide stance and the universal habits every other lens extends. No lens replaces it.

If this vault is new

A freshly installed vault has the framework's floor and nothing about this project. It is structurally valid and not yet worth much. Three things turn that around, in order:

  1. Survey the project with sm_documentation__survey_project if you have not. It is a census of what is actually on disk, so the first lens is written against the real project rather than a guess at it.
  2. Author the first lens. Compile !lens-crafter and treat it as an interview, not a generator: agree the boundaries with whoever owns the project and write the lens from their answers. Write one lens rather than five — a lens honestly about one component beats a survey of everything.
  3. Edit this document. The hard rules below are the installer's defaults and are almost certainly wrong for you in at least one place. Replacing them is the point — this file is yours now.

Delete this section once the vault has a lens or two. It has done its job.

Hard rules

These apply in every session, under every lens. A fresh agent reading this document should treat them as non-negotiable defaults. They are also a starting set — the rules that matter most in a given project are the ones its owner adds here.

  1. Draft and explain before executing on code. For any code change, describe what you intend to do and why before writing a line. Give the user a chance to redirect. Execution follows explanation, never the other way around.
  2. Ask before editing the entry files. CLAUDE.md and its siblings, and this document, are the session entry point for the whole project. Do not modify them unless asked. If you think one needs updating, say so and wait.
  3. Vault writes are permitted and encouraged. Updating the vault — session logs, references, lens bodies, todos — is part of the work, not a side effect of it, and needs no special approval. The exception is the entry files above.
  4. Never claim something about this project you did not read. Every statement written into the vault should trace to a file, a command's output, or something the user said. A plausible invention is worse than a gap, because a gap is visible.
  5. An artifact is done when it validates, not when it is written. Run sm_documentation__validate_docs against what you just saved and fix every error before moving on. Warnings are advisory; errors are not.

Lenses

Compile the lens matching the work before starting it — call sm_documentation__compile_lenses { lenses: ["name"] } and read the composed Know/Care back, rather than opening the lens file directly. Lenses are description-triggered: match the task against the Why column and pick the name. Under Claude Code the !name shorthand resolves to that same call, not a separate mechanism. The compile step is the Starmind built-in for every host; a host that does not hold it directly reaches it through the door its entry file names.

This table mirrors each lens's own frontmatter. No built-in regenerates it today, so after adding or removing a lens, copy the row's text from the lens's frontmatter rather than paraphrasing it — a row written from memory silently drifts from the real thing.

Stacking

Multiple lenses can apply at once. Precedence is declaration order — the first is primary and overrules on conflict; the rest contribute their Know and Care to the composite. This is not a convention layered over compilation, it is sm_documentation__compile_lenses's own rule: pass every active lens as one ordered lenses array, index 0 wins ties.

Stacking is for human-driven sessions, because the human is the conflict resolver in real time. Lenses are deliberately inclusive — overlapping domains are a feature, not a modelling error to be normalised away.

Contracts

A contract is a procedure — a Do the session follows, where a lens is a Know + Care it wears. It is a first-tier primitive in the same way a lens is, and every contract is invocable. There are two ways in, and they are the same invocation: explicitly, as #name ( #plan, #close ), or by description — "let's make a plan" invokes plan exactly as #plan does. Match the request against a contract's When. One token per contract; the phase is named in plain language.

Either way, fetch it with sm_documentation__get_doc { path: "contracts/{name}.html" } and read it whole — a contract is fetched, not compiled, and one that is summarised on the way in has lost its steps. Invoking a contract enters its procedure; it does not promise to finish it now. Close resolves in one sitting, a plan can take a week.

Steps that belong to the human stop and wait for the human. That friction is deliberate: agentic work moves faster than it can be checked, and contracts are where the output is validated before the next step builds on it. Every contract lives in the contracts folder.
