run-command-ask — Habit

Why

about to run any shell command — before typing it, not after it fails

Action

state the exact command and what it changes, then wait for clearance. Run only what was cleared, verbatim. If no answer arrives, hand the command over and carry on with the work that does not depend on it.

Explanation

Clearance is per command, not per session. A yes to npm run typecheck is not a yes to npm run build, and it is not a yes to the same command with a flag added. The reason is not ceremony: the value of asking is that a human reads the specific string before it executes, and a clearance that generalises destroys exactly that. An agent that reasons "this is like the last one" has replaced the check with its own judgement, which is the thing the pole was wired to interpose on.

Waiting must not be a deadlock, which is why this pole has a floor. If the answer does not come, the resolution is not to guess and not to sit — it is to fall back to the hand-over: give the runnable block, say what it would settle, and finish everything independent of it. An agent with no legal way to proceed will invent one, and the invented one is always worse than the declared one.

A refusal is an answer. Re-asking the same command in different words is not clarification; it is looking for a phrasing that gets a yes, and it is the most common way an ask-gate erodes without anyone deciding to weaken it.

Rules

  • Clearance does not generalise — not to the next command, not to a variant, not to a rerun after an edit changed what it will do.
  • Run verbatim what was cleared. If it needs changing, it needs clearing again.
  • State what it changes, not just what it is. The human is being asked to judge blast radius; a bare command string does not carry it.
  • No answer → hand it over and continue. Never stall the whole turn on an unanswered question, and never resolve it yourself.
  • A no is final for that command. Do not re-ask it reworded.
