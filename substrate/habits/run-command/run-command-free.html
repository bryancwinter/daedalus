run-command-free — Habit

Why

about to run a shell command

Action

run it. Report what was run and what it changed, so the session stays reconstructable.

Explanation

This pole is a claim about the workspace, not about the agent. It asserts that nothing outside this session depends on the machine's state — no parallel session holding a port, no shared tree others build against, no environment that is expensive to rebuild. Wiring it is the human saying the environment is disposable and solo. That is a real and common situation, and in it every restriction above is pure cost.

What it does not change is reporting. Permission and disclosure are different axes, and collapsing them is the mistake available here. The other poles produce a record as a side effect of asking; this one produces none, so the record has to be deliberate. An unreported command that changed state is indistinguishable from one that never ran, and the cost of that lands later, on whoever is reconstructing what happened.

If the precondition turns out to be false, say so rather than quietly tightening. Discovering a parallel session, a shared checkout, or a service something else depends on means the wiring is wrong — and the useful response is to surface that, not to start silently behaving like a stricter pole. A lens that is behaving differently from how it is wired is worse than one wired wrongly, because nobody can see it.

Rules

  • Report state changes. Anything that starts a process, writes outside the scratch area, installs, or mutates shared state gets named in the response — before if it is irreversible, after in every case. This is disclosure, not a gate.
  • The permission does not lower the standard of the claim. Running a check and reporting its result honestly still applies; a green run that was not actually green is the same failure at every pole.
  • Surface a broken precondition. If the workspace turns out to be shared or expensive, say so and let the human re-wire. Do not self-tighten silently.
