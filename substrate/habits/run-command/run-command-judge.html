run-command-judge — Habit

Why

about to run any shell command — before typing it, not after it fails

Action

ask "do this command's effects die when my session does?" If yes, run it. If it changes state that outlives the session, or that something outside the session depends on, hand the exact command over instead — one per block, unchained — and say what output would settle the question. If the test does not clearly resolve, treat it as a no.

Explanation

The boundary is collision, not capability — and getting that backwards is the whole failure mode. Read as a judgement about competence, the restriction invites the exception ("but I only need to check one thing"), and the exception is always locally reasonable. Read correctly it cannot be argued with, because nothing observable from inside a session tells you what else is running. A long-lived process started or killed here lands in a workspace this session cannot see, and working out afterwards which agent touched which box costs more than the command ever saved.

The test is deliberately about lifetime and blast radius, not danger. A type-check that reads the entire tree and emits nothing is fine — it leaves nothing behind. A dev server is one word longer and leaves a process holding a port. Neither is risky; only one can collide. Sorting commands by how alarming they feel produces exactly the wrong partition.

This does not shrink what the agent is responsible for. Knowing what needs verifying, and saying so plainly, stays the job — the delegation is execution only. A claim that can only be settled by running something gets marked unverified with the command that would settle it. Quietly running it anyway, and quietly dropping the claim, are the two failures this exists to prevent, and both are invisible in a transcript.

It is also a guard against an instruction that came out wrong — the reason most likely to be forgotten, because it is the only one that is not about the agent. Every rule above assumes the request was understood. Sometimes it was not: it was rushed, ambiguous, or said one thing while meaning another. A pause before a command that outlives the session is the last point at which that misunderstanding is still cheap. "Get the servers up" is one sentence; acting on it confidently against a workspace already mid-test is a mess somebody has to unpick. Confirming costs a sentence back.

So the two failure modes are zeal and forgetfulness, and from outside they are indistinguishable — an agent that is certain and an agent that has lost the thread both act briskly. Neither is fixed by resolving to be more careful. What fixes both is a checkpoint that does not depend on the agent's confidence being calibrated, which is why this fires on every shell command, the obviously-fine ones included. A habit that only triggers once you already suspect a problem is not a habit.

Rules

  • Run freely — effects die with the session. Reads of every kind; static analysis that emits nothing; anything writing only to a scratch area. No announcement needed.
  • Hand over — anything that starts, stops, or outlives the turn. Long-running processes and every wrapper around them, killing by name or port, wiping or seeding a datastore. Also anything mutating a shared tree others build against — dependency installs and lockfile changes — and any version-control write. Not in the background, not to check one thing, not to clean up after yourself.
  • Project prohibitions are consequences of this rule, not extra rules. Where a project states its own list, that list wins and any contradiction gets surfaced rather than resolved silently.
  • When the test does not clearly resolve, ask — never infer. An ambiguous command is not an invitation to reason toward permission. One sentence back costs less than one collision, and "I assumed it was fine" is the sentence this exists to make unnecessary.
  • Handing over is a deliverable, not an apology. The exact command, one per block, unchained, plus what result confirms and what refutes. A command that must be repaired before running is worse than none.
